## 1. Project Overview

| Field | Value |
|---|---|
| **Project name** | `fanrio-auth` — SAP BDC Authorization Wizard |
| **Backend** | SAP CAP (Node.js) — OData v4 service |
| **Frontend** | React + Vite + MUI (Material UI) |
| **Database (dev)** | SQLite (`sqlite.db`) — managed exclusively by `cds deploy` |
| **Database (prod)** | SAP HANA |
| **Purpose** | Manages role-based authorization for SAP BDC / DataSphere. Creates, assigns, and replicates authorization roles to HANA flat tables that BDC reads to enforce row-level access. |
| **OData base path** | `/odata/v4/auth/` |
| **Dev server** | `npm run dev` from project root (runs CAP + Vite concurrently) |

## 2. Critical Rules

> [!CAUTION]
> **NEVER delete or overwrite any file without reading its current contents first.** Files frequently contain non-obvious wiring and side effects.

> [!CAUTION]
> **NEVER rename a CDS entity without updating ALL of the following in one atomic change:**
> - `db/schema.cds` (entity definition)
> - `srv/authorization-service.cds` (OData projection)
> - Every CSV seed file in `db/data/` whose name references the entity (pattern: `fanrio.auth-<EntityName>.csv`)
> - Every `require`/import in `srv/` that references the old entity name
> - Every call in `app/catalog/src/api.js` that references the old OData path
> - Every frontend component that destructures, renders, or filters the entity

> [!CAUTION]
> **NEVER directly edit, import, or run SQL against these files:**
> - `sqlite.db`, `sqlite.db-shm`, `sqlite.db-wal` — managed exclusively by `npx cds deploy`
> - Anything inside `gen/` — auto-generated by `cds build`, always overwritten on next build
> - Anything inside `node_modules/`

> [!WARNING]
> **ALWAYS run `npx cds deploy` after any change to `db/schema.cds`.** Without this, the SQLite schema will be out of sync with the entity definitions and the dev server will error on startup or silently use stale schema.

> [!WARNING]
> **ALWAYS run `npm run test` after any backend change.** The test suite in `test/` covers entity CRUD, authorization enforcement, and the DRAGE engine.

> [!WARNING]
> **ALWAYS run `npm run build --prefix app/catalog` after significant frontend changes** to verify the production bundle compiles without TypeScript/Vite errors. Do not assume dev-mode success equals prod success.

> [!WARNING]
> **NEVER add a new handler file to `srv/handlers/` without also importing and calling its `registerXxx` function inside `srv/authorization-service.js`.** Handler files that are not wired in are silently ignored by CAP.

> [!WARNING]
> **NEVER add a new frontend API function in a component file.** All OData calls MUST live exclusively in `app/catalog/src/api.js`. Components call these exported functions; they do not call `fetch` directly.

> [!NOTE]
> The simulated-user header `x-simulated-user` is the dev-mode auth mechanism. In tests, `authGuard.getUserId()` always returns `'admin'`. In dev, the active simulated user is set via `api.js:setSimulatedUser()` and sent with every request. There is no real SAML/OAuth in development.

## 4. Data Model Key Concepts

### Role Types

| Type | Meaning |
|---|---|
| `SINGLE` | Standalone role — its own restrictions only. |
| `DERIVED` | Inherits restrictions from one or more parent roles (via `RoleInheritance`). |
| `ORG_BASED` | Auto-generated from an org node by `orgRoleGeneratorService.js`. Linked to an `OrgNode`. |

### Restriction Filter Types

| Type | Value format stored in DB | Notes |
|---|---|---|
| `SINGLE_VALUE` | Plain string | Exact match on one value. |
| `MULTI_VALUE` | Comma-separated or JSON array | Multiple discrete values. |
| `RANGE` | JSON `{"from": "...", "to": "..."}` | Inclusive range. |
| `BT` | JSON `{"from": "...", "to": "..."}` | SAP BT (between) — parsed identically to RANGE. |
| `HIERARCHY` | Node ID string | Hierarchy node key for BDC hierarchy filter. |
| `PATTERN` | Glob/wildcard string | Pattern-matched filter. |

### Streams

- Hierarchical classification tree for roles (analogous to departments or data domains).
- **Each Stream node auto-creates a HANA flat table** named `[stream_name]_flat_authorizations` on all active HANA connections at the moment it is created (`streamHandler.js`).
- Streams are used to group roles and to namespace their HANA flat tables.

### HANA Replication Flow

1. User is assigned to a role via `createAssignment`.
2. `assignmentHandlers.js` fires `after CREATE` → calls `syncAssignmentToHana(id, userId, roleId, false)` in `cds.spawn` (non-blocking).
3. `hanaReplicationService.js` fetches the full ancestry chain of the role, resolves effective restrictions, computes the Cartesian product of all restriction field values.
4. Flattened rows are written to:
   - The default `AUTHORIZATION_FLAT` table (all roles).
   - The stream-specific `[stream_name]_flat_authorizations` table (for the role's stream).
5. A replication queue entry (`Replications` entity) is created via `queueReplication()`.
6. On `triggerReplication` action, `replicationQueueService.js` calls the BDC task chain to push the rows to SAP BDC/DataSphere.

### DRAGE — Dynamic Role & Assignment Generation Engine

- Rules stored in `DynamicGenerationRules` entity; field mappings in `DynamicRuleFieldMappings`.
- `syncDynamicRule(ruleId, cds)` in `dynamicSyncService.js`:
  - Source can be `LOCAL_DB` (reads a local entity) or a BDC Asset (fetches via `BdcClient.fetchRelationalValues`).
  - Optional `sourceFilterCondition` (JSON `{field, value}`) filters master records in-memory.
  - Groups records by responsible user → creates or updates generated roles + assignments.
  - Tracks generated resources in `GeneratedResourceMap` to enable idempotent re-sync and cleanup.
- Triggered from `DynamicRulesView.jsx` via `syncDynamicRule(ruleId)` API call, or by the `syncDynamicRule` OData action.

### AppAuthorizations & Permission Model

- `AppAuthorizations` entity: one row per user, keyed on `userId`.
- **Open Demo Mode**: if the `AppAuthorizations` table is empty and `VITE_ALLOW_DEMO_MODE !== 'false'`, `getSessionPermissions()` returns a synthetic super-admin object with all flags `true`. This is the default dev behavior.
- Permission flags checked by `authGuard.requirePermission()`:

| Flag | Controls access to |
|---|---|
| `isSuperAdmin` | Bypasses ALL permission checks |
| `canManageAppUsers` | `AppAuthorizationsView` |
| `canManageOrgRoles` | Org-based role generation |
| `canManageSingleRoles` | Single role CRUD |
| `canManageDerivedRoles` | Derived role CRUD |
| `canAssignRoles` | `RoleAssignments` CREATE/DELETE |
| `canViewAuditLogs` | `AuditLogsView` |
| `canManageSettings` | `AdministrationView` (BDC settings, restriction fields) |
| `allowedEnvironments` | JSON array, `'ALL'`, or `'*'` — scopes environment access |

## 7. Common Safe Patterns

### Adding a new OData entity

1. Add entity definition to `db/schema.cds`.
2. Add projection to `srv/authorization-service.cds`.
3. Create seed file `db/data/fanrio.auth-<EntityName>.csv` (can be empty header-only).
4. Run `npx cds deploy`.
5. Add CRUD functions to `app/catalog/src/api.js`.

### Adding a new handler file

1. Create `srv/handlers/<entityName>Handlers.js`.
2. Export `registerXxxHandlers(service, entities, deps)`.
3. Open `srv/authorization-service.js`, import the new file, and call `registerXxxHandlers(...)` inside the service init block.
4. Do NOT put business logic directly in `authorization-service.js`.

### Adding a new service module

1. Create `srv/services/<featureName>Service.js`.
2. Export named functions.
3. Import the functions in whichever handler or other service file needs them.
4. Inject via the `deps` parameter pattern where possible to keep modules testable.

### Adding a new frontend view

1. Create `app/catalog/src/components/<FeatureName>View.jsx`.
2. Import it in the appropriate parent — either `App.jsx` (top-level route) or an existing tabbed view.
3. Add any new API calls to `app/catalog/src/api.js` first; then call them from the component.
4. Gate the view behind the appropriate permission flag using `usePermissions()` from `PermissionsContext`.

### Adding a new permission-gated action

1. Add the permission flag to the `AppAuthorizations` entity in `db/schema.cds`.
2. Add it to the default objects returned in `authGuard.getSessionPermissions()` (both the empty-table Demo Mode object and the "user not found" fallback object).
3. Call `requirePermission(permissions, 'newFlag', req)` in the relevant handler's `before` hook.
4. Update `app/catalog/src/context/PermissionsContext.jsx` to expose the new flag.

### Key dev defaults

- **Default super admin user in dev**: `admin` (returned by `authGuard.getUserId()` in test env; set via `x-simulated-user: admin` header in dev).
- **Default simulated user in frontend**: `jdoe` (see `api.js` line 3 — `activeSimulatedUser = 'jdoe'`). Change via `setSimulatedUser()` or the user switcher in the UI.
- **Open Demo Mode**: Active by default when `AppAuthorizations` table is empty. Grants all permissions to any user. Disable by setting `VITE_ALLOW_DEMO_MODE=false`.
- **Mock BDC URLs**: `urlUtils.isMockUrl()` detects placeholder BDC connection URLs and skips real HTTP calls, returning mock data instead.
- **No real auth in dev**: There is no SAML/OAuth flow locally. The `x-simulated-user` header is the only auth mechanism.

## 9. Pitfall Reference

| Pitfall | Why it happens | How to avoid |
|---|---|---|
| Handler not firing | Registered in handler file but not wired in `authorization-service.js` | Always call `registerXxx()` in the service init block |
| Schema out of sync | `db/schema.cds` edited but `npx cds deploy` not run | Run deploy immediately after every schema change |
| CSV seed not loading | File not named exactly `fanrio.auth-<EntityName>.csv` | Match entity name exactly, including capitalisation |
| 400 on assignment create | Role has no restrictions — `assignmentHandlers.js` rejects it | Add at least one restriction to the role first |
| HANA sync silently skipped | Mock URL detected by `isMockUrl()` | Expected in dev — only runs against real HANA connections |
| Permission check bypassed | `isSuperAdmin: true` skips `requirePermission` and `requireEnvironment` | Do not set `isSuperAdmin: true` in production seeds |
| Replication duplicate entries | `queueReplication()` deduplicates by `roleName + environment + status=Open` | If you rename a role, the old queue entry may never resolve — update or clear it |
| Test user is always `admin` | `authGuard.getUserId()` hardcodes `'admin'` in test env | Do not rely on `x-simulated-user` in test assertions — it is ignored |
